# Camellia App

Реализация шифра Camellia на Python.

## Контекст проекта

Мы пишем десктопное приложение на Python, которое шифрует и расшифровывает **файлы любого типа** (текст, изображения, аудио, видео — что угодно) алгоритмом **Camellia** согласно **RFC 3713**.

Проект разделён на три модуля:

| **Модуль** | **Автор** | **Назначение** |
| :-: | :-: | :-: |
| `camellia_core.py` | Участник 1 | Ядро: S-боксы, F-функция, P-функция, ключевое расписание |
| `camellia_engine.py` | Участник 2 | Движок: раунды, FL/FL⁻¹, `encrypt()`/`decrypt()`, разбивка файла на блоки |
| `main.py` + `test_camellia.py` | Участник 3 | GUI, интеграция, тесты на векторах из RFC 3713 |

**Текущий статус:** `camellia_core.py` полностью готов. Он реализует криптографические примитивы и ключевое расписание. Модуль не работает с файлами — он принимает ключ и возвращает список подключей, а также умеет вычислять F-функцию.

## 📦 Публичный API модуля `camellia_core.py`

### 1. Функция `generate_subkeys(key: bytes) -> list[int]`

Генерирует все подключи из исходного ключа.

**Вход:**

- `key` — байтовая строка длиной ровно 16, 24 или 32 байта (128, 192 или 256 бит).

- При другой длине выбрасывается `ValueError`.

**Выход:**

- `list[int]` — список 64-битных целых беззнаковых подключей.

- Длина списка: **26 элементов для 128-битного ключа**, **32 элемента для 192/256-битного ключа**.

- Порядок элементов — **строго тот, в котором они используются в цикле шифрования** (см. таблицу ниже). Это уже готовый «поток» подключей для последовательного чтения.

**Пример:**

python

```
from camellia_core import generate_subkeys


subkeys = generate_subkeys(bytes.fromhex("0123456789abcdeffedcba9876543210"))

print(len(subkeys))   # 26 для 128-битного ключа

print(hex(subkeys[0]))  # kw1
```

### 2. Функция `_F(f_in: int, ke: int) -> int`

F-функция Camellia — главный криптографический примитив раунда.

**Вход:**

- `f_in` — 64-битное беззнаковое целое (входные данные половины блока).

- `ke` — 64-битное беззнаковое целое (раундовый подключ).

**Выход:**

- 64-битное беззнаковое целое.

**Важно:** имя начинается с подчёркивания (`_F`) — это сделано по соглашению «внутренняя функция модуля», но **Участник 2 должен импортировать и использовать её напрямую**:

python

```
from camellia_core import _F
```

### 3. Константы

python

```
MASK8, MASK32, MASK64, MASK128        # маски разрядности

SIGMA1 ... SIGMA6                     # константы ключевого расписания

SBOX1, SBOX2, SBOX3, SBOX4            # таблицы замен (списки из 256 чисел)
```

Обычно Участнику 2 и 3 эти константы не нужны напрямую — они нужны только внутри `camellia_core.py`.

## 🔑 Точный порядок подключей (по индексам)

Это самое важное для Участника 2. `generate_subkeys()` возвращает элементы в порядке ниже — **не нужно ничего сортировать или переставлять**, просто читайте список по индексам.

### Для 128-битного ключа (26 элементов)

| **Индекс** | **Имя** | **Назначение** |
| :-: | :-: | :-: |
| 0 | `kw1` | Пре-whitening (XOR с левой половиной блока до раундов) |
| 1 | `kw2` | Пре-whitening (XOR с правой половиной блока) |
| 2 | `k1` | Раунд 1 |
| 3 | `k2` | Раунд 2 |
| 4 | `k3` | Раунд 3 |
| 5 | `k4` | Раунд 4 |
| 6 | `k5` | Раунд 5 |
| 7 | `k6` | Раунд 6 |
| 8 | `ke1` | FL-слой (после раунда 6) |
| 9 | `ke2` | FL-слой |
| 10 | `k7` | Раунд 7 |
| 11 | `k8` | Раунд 8 |
| 12 | `k9` | Раунд 9 |
| 13 | `k10` | Раунд 10 |
| 14 | `k11` | Раунд 11 |
| 15 | `k12` | Раунд 12 |
| 16 | `ke3` | FL⁻¹-слой (после раунда 12) |
| 17 | `ke4` | FL⁻¹-слой |
| 18 | `k13` | Раунд 13 |
| 19 | `k14` | Раунд 14 |
| 20 | `k15` | Раунд 15 |
| 21 | `k16` | Раунд 16 |
| 22 | `k17` | Раунд 17 |
| 23 | `k18` | Раунд 18 |
| 24 | `kw3` | Пост-whitening (XOR с левой половиной после последнего раунда) |
| 25 | `kw4` | Пост-whitening (XOR с правой половиной) |

### Для 192/256-битного ключа (32 элемента)

| **Индекс** | **Имя** | **Назначение** |
| :-: | :-: | :-: |
| 0 | `kw1` | Пре-whitening |
| 1 | `kw2` | Пре-whitening |
| 2–7 | `k1`–`k6` | Раунды 1–6 |
| 8–9 | `ke1`, `ke2` | FL-слой |
| 10–15 | `k7`–`k12` | Раунды 7–12 |
| 16–17 | `ke3`, `ke4` | FL⁻¹-слой |
| 18–29 | `k13`–`k24` | Раунды 13–24 |
| 30 | `kw3` | Пост-whitening |
| 31 | `kw4` | Пост-whitening |

**Итого:** для 256 бит 24 раунда, для 128 бит — 18 раундов. Формула длины: `4 (kw) + 4 (ke) + N (раундов)`.

## 🧭 Как Участнику 2 строить `camellia_engine.py`

Задача: реализовать полный цикл шифрования/дешифрования одного 128-битного блока и обвязку для работы с файлами.

### Схема шифрования одного блока (128 бит)

1. Разбить 128-битный блок на две 64-битные половины: `D1` (левая), `D2` (правая).

2. `D1 ^= kw1`, `D2 ^= kw2`.

3. Для каждого раунда `r = 1..N`:

   - Если перед раундом по порядку идёт `ke`-ключ — выполнить **FL** (или **FL⁻¹** в зависимости от позиции) над `D1` и `D2` с этим `ke`.

   - Иначе — выполнить раунд с ключом `k_r`:

     - `D1 ^= F(D2, k_r)`

     - Обменять `D1` и `D2` (кроме финального шага, см. RFC).

4. `D2 ^= kw3`, `D1 ^= kw4` (порядок зависит от чётности — в RFC 3713, раздел 2.1).

5. Собрать блок обратно: `(D1 << 64) | D2`.

**Конкретный порядок операций** — строго как в RFC 3713, раздел 2.1. Используйте индексы из таблицы выше: `subkeys[0]` — это `kw1`, `subkeys[2]` — `k1` и т.д.

### FL-функция (реализуется Участником 2, не входит в ядро)

python

```
def FL(x: int, ke: int) -> int:

    """x — 64-битные данные, ke — 64-битный ключ."""

    x1 = (x >> 32) & MASK32

    x2 = x & MASK32

    k1 = (ke >> 32) & MASK32

    k2 = ke & MASK32

    x2 ^= ((x1 & k1) << 32) | 0  # см. RFC 3713 (2.5) — точная формула

    # ... вернуть ((x1 << 32) | x2)
```

Формулу FL и FL⁻¹ берите дословно из **RFC 3713, раздел 2.5**. Это единственная часть алгоритма, которую Участник 2 пишет самостоятельно (не считая обвязки).

### Дешифрование

Дешифрование Camellia — это тот же цикл, но с **обратным порядком подключей**. В RFC 3713, раздел 2.1, указано, как переставлять `kw`, `k` и `ke` для дешифрования. Не переизобретайте — просто повторите схему из RFC.

### Работа с файлами (важно!)

- Файл читается **бинарно**, порциями по 16 байт.

- Блочный шифр требует дополнения (padding) последнего неполного блока — используйте **PKCS\#7** (он стандартен и прост).

- Для реальной работы с файлами используйте режим **CBC** или **CTR** (реализация — на Участнике 2). ECB использовать не рекомендуется, но для тестов сгодится.

- Формат зашифрованного файла стоит определить в шапке (например, магическое число + IV + длина оригинального файла), чтобы при дешифровании всё корректно восстанавливалось. Согласуйте формат с Участником 3 до начала работы.

## ✅ Как Участнику 3 писать тесты

- **Тестовые векторы** берите из **RFC 3713, Приложение A** — там есть эталонные примеры для 128, 192 и 256 бит.

- **Первый тест** — проверка F-функции на одном входе из RFC.

- **Второй тест** — проверка `generate_subkeys()` для ключа `0123456789abcdeffedcba9876543210` (128-бит): ожидаемые подключи приведены в RFC.

- **Третий тест** — end-to-end: `encrypt(plaintext) == expected_ciphertext` из RFC.

- **Четвёртый тест** — round-trip: `decrypt(encrypt(x)) == x` для файлов разного типа (текст, случайные байты, картинка).

- Используйте `pytest` или стандартный `unittest`.

## ⚠️ Известные ограничения ядра

- Модуль **не выполняет** FL/FL⁻¹, разбиение на раунды и работу с файлами — это задачи Участника 2.

- Модуль **не выполняет** паддинг и режимы (CBC/CTR) — это тоже Участник 2.

- `generate_subkeys()` выбрасывает `ValueError` при неверной длине ключа — Участник 3 должен обработать это в GUI.

- Имя `_F` начинается с `_`, но функция **публичная по факту использования**. Если хотите, можно переименовать в `F` — согласуйте внутри команды.
